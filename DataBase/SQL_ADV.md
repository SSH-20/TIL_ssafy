# SQL ADVENCDED
## 관계
> 여러 테이블 간의 (논리적) 연결

## ***JOIN이 필요한 순간***
- 테이블을 분리하면 데이터 관리가 쉬워지지만 연관 정보는 여러 테이블에 나뉨
- 분산된 연관 데이터를 하나의 결과 집합으로 조회할 때 JOIN 사용

## JOIN clause
> 둘 이상의 테이블에서 데이터를 검색하는 방법

## INNER JOIN clause
> 두 테이블에서 ON 조건을 만족하는 행 조합만 반환

## LEFT JOIN clause
> 오른쪽 테이블의 일치하는 레코드와 함께 왼쪽 테이블의 모든 레코드 반환

## RIGHT JOIN clause
> 왼쪽 테이블의 일치하는 레코드와 함께 오른쪽 테이블의 모든 레코드 반환
* 일반적으로 mysql은 right join을 left로 치환하여 연산한다.
* 위치만 바꾼 left와 같지만, 필요한 상황이 있다.

## SLEF JOIN clause
> 동일한 테이블을 서로 다른 별칭으로 두 번 이상 참조하여 ON 조건을 만족하는 행 조합을 반환
* 주로 계층적 데이터 구조를 표현하거나 동일 테이블 내에서 특정 관계를 찾을 때 사용

## SUbQuery
> 하나의 SQL문 안에 포함되어 있는 또 다른 SQL 문
* 복잡한 데이터를 이용하여 검색하거나 값을 비교할 때 사용

### **SubQuery 사용법
* 서브쿼리는 괄호로 감싸서 사용
* 서브쿼리 사용 가능한 곳
    - SELCET 절
        - 값처럼 사용하는 스칼라 서브쿼리는 하나의 열, 최대 한 행을 반환
    - FROM 절
        - 중간 집계나 계산, 결과 재사용, 조인 조건 단순화에 사용
    - WHERE 절
        - 특정 조건을 만족하는 데이터를 필터링하거나 검색할 때 사용
    - 그 외 HAVING 절, INSERT 문으 VALUES 절, UPDATE 절에서 사용 가능

**SubQuery 종류**
- 단일 행 서브쿼리 (Single-row SubQuery)
- 다중 행 서브쿼리 (Multi-row SubQuery)
- 다중 열 서브 쿼리 (Multi-column SubQuery)

## **단일 행 서브쿼리**
- 스칼라 서브쿼리는 하나의 열에서 0행 또는 1행을 반환
- 비교 연산자 (=, <, >, <=. >=, <>) 와 함께 사용

### **단일 행 서브쿼리 정리**
* 2행 이상이면 오류 발생
* WHERE 절이나 SELECT 절에서 값처럼 사용하는 것이 일반적
* 비교 연산자와 함께 사용할 때 결과 행 수를 반드시 확인

### ***단일 행 서브쿼리 활용***
* SELECT, FROM, WHERE 모든 절에서 사용 가능하다.

## **다중 행 서브쿼리**
- 실행 결과가 0행, 1행 또는 여러 행일 수 있는 서브쿼리
- IN, ANY, ALL, EXISTS, NOT EXISTS 연산자와 함께 사용

### ***다중 행 서브쿼리 활용***
* FROM 절에서 테이블을 가져올 때, 애초부터 조건에 걸러진 테이블을 가져올 떄 사용 가능

### **다중 행 서브쿼리 정리**
- 다중 행 서브쿼리는 0행, 1행 또는 여러행을 반환할 수 있음
    - 여러 행과 비교할 때 IN, ANY, ALL을 사용
- 행의 존재 여부는 EXISTS, NOT EXISTS로 확인
    - NOT IN은 결과에 NULL이 있으면 UNKNOWN이 될 수 있음

## **다중 컬럼 서브쿼리**
- 실행 결과가 둘 이상의 컬럼을 반환하는 서브쿼리
- 좌우 열 개수는 같아야 함
- = 비교는 최대 한 행, (a, b) IN (..)은 여러 행 허용 EXISTS는 SELECT 목록의 열 수를 비교하지 않음

### **다중 컬럼 서브쿼리 정리**
- 다중 컬럼 서브쿼리는 둘 이상의 컬럼을 반환
    - 행 비교 시 좌우 열 개수가 같아야 함
    - = 비교는 최대 한 행, IN 비교는 여러 행을 허용

# Database Index
## Index란?
- 데이터베이스에서 데이터를 보다 빠르게 찾기 위해 사용되는 자료구조
- 책에서 원하는 부분을 처음부터 찾는 것이 아닌 목차를 보고 빠르게 찾을 수 있는 방식과 유사

## **Index 사용의 장점**
- 적절한 쿼리에서 읽기 I/O를 줄일 수 있음
- 조건에 맞는 행을 더 빠르게 찾을 수 있음

## **Index 사용의 단점**
- 각 인덱스는 추가 저장 공간을 사용
- INSERT, UPDATE, DELETE 시 인덱스 갱신 비용이 추가됨

## **Index 종류**
1) 기본 인덱스
    - 일반적으로 선언했을 때의 인덱스
    - 인덱스로 설정된 컬럼의 데이터에 NULL 값이 존재할 수 있음
    - 인덱스가 설정된 컬럼의 데이터에 중복이 있을 수 있음

2) 유니크 인덱스
    - UNIQUE 키워드와 함께 선언했을 때의 인덱스
    - 인덱스를 설정할 컬럼의 데이터들은 각각 교유한 값이어야 함
        - 중복된 데이터가 존재할 시 'Duplicate entry' 에러 발생
        - 컬럼을 추가로 구성하여 고유한 값으로 구성하면 해결

## VIEW
실행 시 옵티마이저가 쿼리를 MERGE하거나 내부 임시 테이블로 구체화할 수 있음

## **VIEW의 장점**
- 편리성
    - 복잡한 쿼리를 미리 정으된 뷰로 만들어 단순화 가능
- 보안성
    - 사용자가 데이터베이스 일부만 볼 수 있도록 제한 가능
- 재사용성
    - 동일한 뷰를 여러 쿼리에서 사용 가능

## **VIEW 생성하기**
- CREATE VIEW 이후 뷰 이름 설정
    - 팀의 명명 관례로 v_접두사를 사용할 수 있음 (필수 X)
- AS 키워드 이후 SELECT 구문을 작성
- 생성한 view_name으로 뷰를 조회

## B-tree
- 가장 일반적으로 사용하는 Index 구조
- 균형 다진 탐색 트리로 높이를 낮게 유지
- 단일 키 탐색은 트리 높이에 비례해 O(log N) 수준
    - 범위 탐색은 O(log N + K), K는 반환 건수

## 핵심 정리
- JOIN은 어느 쪽 행을 보존하는지 확인
- 서브쿼리는 반환하는 행 수와 열 수를 확인
- 인덱스는 실행계획으로 실제 사용 여부를 확인
