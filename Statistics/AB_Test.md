## **비율 검정**
### **베르누이 시행**
- 베르누이 시행은 결과가 성공/실패 처럼 0 또는 1로만 나오는 한 번의 실험
    - 예시 : 클릭함/클릭안 함, 구매함/구매 안 함
- A/B 테스트의 CTR, CVR, 구매 여부는 대부분 베르누이 데이터로 볼 수 있음
- 한 사용자의 converted 값이 1이면 전환, 0이면 미전환
- 이항분포는 여러 번의 베르누이 시행에서 성공 횟수를 세는 분포
- Bernoulli -> Binomial -> 표본 비율 -> Proportion Z-test 연결

### **표본 비율**
- 표본 비율은 전체 시도 중 성공이 발생한 비율 (모비율을 추정하는데 사용)
    - p-hat = 성공 횟수 / 전체 시행 횟수
    - CTR = Click / Impression
    - CVR = Purchase / Impression 또는 Purchase / User
    - Traffic Split = B 그룹 사용자 수 / 전체 사용자 수

### **표본비율의 표준오차**
- 표준오차(Standard Error)는 표본비율이 표본을 다시 뽑을 때 ***얼마나 흔들리는지***를 나타내는 값
    - 이항분포 X ~ Binomial(n, p)에서 표본 비율은 p-hat = X/n
    - 표본비율의 표준오차 : SE = sqrt(p(1-p) / n)
    - n이 커질수록 SE는 작아짐 -> 큰 실험일수록 작은 차이도 더 잘 검출
    - p를 모르면 실제 분석에서는 관측 비율 p-hat
    - 두 집단 비교에서는 통합 비율(pooled proportion)을 사용하기도 함

### **정규근사와 Z-Score**
- 정규근사는 표본 수가 충분히 클 때 표본비율의 분포를 정규분포로 보는 방법
- 표본 수가 충분히 크면 표본비율의 분포는 중심극한정리에 의해 정규분포에 가까워짐
- Z-score는 관측값이 기대값에서 표준오차 몇 개만큼 떨어져 있는지를 나타냄
    - Z = (관측비율 - 기대비율) / 표준오차 -> 기준에서 표준오차만큼 얼마나 떨어져 있나?
    - |Z|가 클수록 우연히 나온 차이라고 보기 어려움
    - 95% 기준 양측 검정에서는 보통 |Z| 1.96 이면 귀무가설을 기각

### **단일 비율 Z-test (one-proportions Z-test)
- 단일 비율 Z-test는 관측된 비율이 기대 비율과 다른지 검정하는 방법
    - 귀무가설 H0 : 실제 비율 p = 기대비율 p0
    - 대립가설 H1 : 실제 비율 p != 기대비율 p0

### **단일 비율 Z-test 계산 흐름**
1. 기대 비율 p0와 표본 수 n을 정함
    - 예 : 기대 비율이 50% 라면 p0 = 0.5
2. 관측 비율 : p-hat을 계산
    - 예 : 전체 10,000명 중 B 그룹 5,200aud -> p-hat = 0.52
3. 표준오차(SE) = sqrt(p0(1-p0)/n)
4. Z = (p-hat - p0) / SE 로 기대값에서 얼마나 벗어났는지 판단

### **두 비율 Z-test (two-proportion Z-test)
- 두 비율 Z-test는 두 집단의 비율 차이가 유의미 한지 검정하는 방법
    - 귀무가설 H0 : pA = pB
    - 대립가설 H1 : pA != pB 또는 pB <= pA
- 예시 : A 전환율 10%, B 전화율 12%일 때 B가 실제로 더 좋은지 확인
    - 비율 차이 / 비율 차이의 표준오차로 Z-score 계산
    - CTR, CVR, 가입률, 구매율 같은 0/1 지표 비교에 사용

### **두 비율 Z-test 계산 흐름**
1. 각 그룹의 표본비율을 계산
    - pA = xA/nA, pB = xB/nB
2. 귀무가설에서는 두 그룹의 실제 전환율이 같다고 가정
    - 공통 전환율 pooled_pool(p_pool) = (xA + xB) / (nA + nB)
3. SE = sqrt(p_pool(1-p_pool)(1/nA + 1/nB))
4. Z = (pB-pA) / SE 로 두 비율 차이의 유의성 판단


## **A/B Test**
### **데이터 기반 의사결정**
- 기술 통계 / 현황 분석
    - 이미 발생한 데이터를 요약하고 현상을 파악하는 분석
        - 지난달 매출은 얼마인가, 어떤 제품이 가장 많이 팔렸는가
- 탐색적 데이터 분석 (EDA)
    - 특정 현상이 발생한 원일을 탐색하는 방법(데이터에서 패턴을 찾는 분석)
        - 지역별 매출 차이는 있는가, 체류 시간이 갈수록 구매율이 높은가
- 예측 분석 (Predictive Analytics)
    - 과거 데이터를 기반으로 미래를 예측하는 분석
        - 특정 사용자가 구매할 확률, 이 고객이 이탈할 가능성
- 실험 기반 분석 (Experimentation)
    - 변수를 의도적으로 변경하여 그 변화가 결과에 미치는 영향을 측정하는 분석 방법
        - 어떤 방법이 실제로 더 좋은 결과를 만드는가?

### **실험 기반 분석**
- 변수를 의도적으로 변경하여 그 변화가 결과에 미치는 영향을 측정하는 분석 방법
    - 동일한 조건에서 두 개 이상의 실험군을 비교
    - 실제 사용자 또는 환경에서 통제된 실험 수행
    - 특정 변화가 결과에 미치는 인과관계(causality)를 검증
- 어떤 방법이 실제로 더 좋은 결과를 만드는가?
- 대표적인 방법 : A/B Test

### **A/B Test 기본 구조**
- 실제 사용자를 대상으로 수행하는 실험
    - 서비스의 기존 버전(Control)과 새로운 버전(Test)을 비교
    - 사용자 트래픽을 랜덤으로 분할하여 실험 진행
    - 두 그룹의 성과 지표(Metric)를 비교하여 효과 검증
- 실험을 위해서는 명확한 가설과 측정 지표가 필요

### **A/B Test 수행**
- A/B 테스트는 가설을 얼마나 지지하는지 통계적으로 검중하는 실험
    - 특정 변경이 서비스 성과에 영향을 미치는지 검증
    - 반드시 명확한 가설(Hypothesis)이 필요
- 예시 : 구매 체크아웃 페이지 A/B 테스트
    - 가설 1 : 새로운 추천 알고리즘이 기존 알고리즘보다 매출을 증가시킬 것이다.
    - 가설 2 : 체크아웃 단계를 줄이면 구매율이 증가할 것이다.

### **좋은 A/B Test 가설 조건**
- 좋은 가설은 변경 대상, 기대 행동 변화, 측정 지표가 함께 있어야 함
    - 나쁜 예 : 버튼을 바꾸면 좋아질 것이다.
    - 좋은 예 : 결제 버튼 문구를 바꾸면 구매 전화율이 증가할 것이다.
    - 구조 : 변경 대상 -> 기대 행동 변화 -> 측정 지표
- 가설과 검정 지표를 먼저 정하고 분석을 시작

### **실험 구조**
- 두 개 이상의 버전을 실제 사용자에게 비교
    - control (A) : 현재 서비스 버전
    - Test (B) : 변경된 새로운 버전
    - 사용자 트래픽을 랜덤으로 분할하여 실험 수행
    - 각 그룹의 성과 지표(Metric)를 비교
- 실제 서비스 환경에서의 특징
    - 보통 프로덕션 환경에서 수행
    - 서비스 내 여러 A/B 테스트가 동시에 진행될 수 있음
    - 한 사용자가 여러 실험에 포함될 수 있음

### **Primary Metric과 Guardrail Metric
- Primary Metric : 실험의 성공 여부를 판단하는 핵심 지표
    - 예 : 구매 전환율, 매출, 클릭률, ARPU
- Guardrail Metric : 약화되면 안 되는 부작용을 확인하는 보호 지표
    - 예 : 이탈률, 환불률, 페이지 로딩 시간, CS 증가, 객단가 하락
- 클릭률이 올라도 구매율이나 매출이 떨어지면 성공으로 보기 어려움

### **A/B Test를 하는 이유**
- 새로운 기능의 변화의 효과를 객관적으로 측정
    - 서비스 변경이 빚니스 지표에 실제로 영향을 미치는지 검증
    - 가설 기반으로 실제 사용자 데이터를 비교
- 서비스 변경에 따른 위험을 최소화
    - 새로운 기능을 전체 사용자에게 바로 적용하면 위험이 존재
    - 일부 사용자에게 먼저 적용하여 문제 발생 가능성 확인
- 빠르게 실험하고 개선하기 위해 (애자일해야 함)
    - 작은 변화 -> 실험 -> 결과 분석 -> 개선
    - 빠른 제품 개선 사이클 구축하며 제품의 발전 속도를 느림
- A/B Test는 효과를 측정하고 위험을 줄이며 빠르게 제품을 개선하기 위한 방법

### **A/B Test를 사용하면 안 되는 경우**
- 어떤 결정은 A/B Test로 판단할 수 없음
- 데이터가 충분하지 않은 경우
- 버그 수정과 같은 명확한 문제 해결이 필요한 경우
- 명확한 가설이 없는 경우
- 비교 대상(Control)이 없는 경우

### **A/B Test 프로세스**
- 가설을 기반으로 실험을 설계하고 결과를 반복적으로 개선하는 과정
- 실험 제안 및 설계
    - 가설기반 실험 제안을 통한 실험 목적
    - 영향 지표, 신뢰수준 및 실험 설계 등
    - 테스트할 기능 및 UI 설계 (MVP)
- 구현 및 QA
    - 실험 기능 구현
    - 트래픽 분할 설정
    - 데이터 수집 확인
- 배포 (Rollout)
- 결과 리뷰 및 반복 개선
    - 실험 결과 분석
    - 다음 실험 설계

### **A/B Test 배포(Rollout)**
- A/B Test는 한 번에 전체 사용자에게 적용하지 않고 점진적으로 확대
- 스모크 테스트 (Smoke Test) - 성과 판단 X
    - 1% 이하 사용자에게 먼저 적용
    - A/B 테스트 설정이 정상 동작하는지 확인
    - 시스템 오류 여부 점검
- 중간 단계
    - 실험 트래픽을 점진적으로 확대
- 최종 단계 문제가 없다면 Winner 버전을 100% 사용자에게 제공
- 핵심 위험을 줄이기 위해 점진적으로 실험 트래픽을 확대

### **A/B Test 분석에 필요한 데이터**
- 사용자 실험 버킷(Bucket) 정보
    - 사용자가 어떤 실험 그룹에 속했는지
    - 누가 A그룹이고 누가 B 그룹인가? -> 보통 RDB나 크기가 크다면 로그파일 형태로 기록
    - experiment_id, variant_id(A/B), user_id, timestamp 등의 정보
- 사용자 행동 데이터 (Funnel 정보)
    - 사용자가 실제로 어떤 행동을 했는지
    - 노출, 클릭, 구매, 매출 등
- 데이터가 데이터 웨어하우슨 ㅏ데이터 레이크로 복사되고 이를 데이터 분석가들이 분석에 용이한 형태로 새로운 테이블을 생성해서 조회

### **A/B Test Traffic**
- Traffic을 A/B로 나누는 방법
- 어떤 ID를 사용할 것인가?
    - 실험 특성에 따라 선택
    - 로그인한 사용자에게만 하는 테스트
    - 모든 방문자에게 하는 테스트
- USER ID
    - 로그인 사용자 기반 실험
    - 사용자 단위 실험 가능
- Device ID
    - 비로그인 사용자 실험
    - 브라우저 쿠키 기반 ID

- 사용자를 A/B 그룹으로 나누느 방법은 크게 두 가지
- 사전 분배 방식
    - 모든 사용자를 미리 A/B 그룹으로 분배
    - 로그인 사용자 기반 서비스에서 적용 가능
    - 신규 사용자, 비로그인 사용자는 적용은 어려울 수 있음
- 동적 분배 방식
    - 사용자가 접속할 때 실시간으로 A/B 그룹 결정
    - 가장 일반적인 방식으로 로그인 여부 관계없이 사용 가능
    - 여러 A/B 테스트가 동시에 실행되면 실험 간 상호작용(Interaction)으로 결과가 왜곡될 수 있음
    * (추천 알고리즘 A/T Test와 UI 디자인 A/B Test를 동시에 진행하는 경우)

### **A/B Test 분석에 필요한 데이터**
- 사용자 실험 버킷(Bucket) 정보
- 사용자를 A/B 그룹으로 나누는 방법
    - Hash 기반 Bucketing
    - variant = hash(experiment_id + user_id) % 100
        - 0 ~ 49 -> Control
        - 50 ~ 99 -> Test 결과
- 같은 사용자는 항상 같은 그룹에 배정
- 실험 중간에 그룹이 바뀌면 실험이 깨짐

### **A/B Test 분석에 필요한 데이터**
- 사용자 행동 데이터 (Funnel 정보)
- 일반적이 서비스
    - 노출(impression) -> 클릭(Click) -> 구매(Purchase) -> 소비(Consumption)
    - 전환율 변화, 사용자 행동 변화, 기능 영향 등을 분석할 수 있음
- 설정
    - 측정하려는 목표
    - 목표까지의 단계
    - 데이터 트래킹

### **A/B Test 결과 분석**
- 실험 분석은 두 데이터를 결합하여 수행 (Bucket Data + Funnel Data Join)
    - 추가적으로 메타 정보 등을 추가하면 다양한 분석에 사용할 수도 있음
    - A/B 그룹의 사용자 수가 의도한 비율대로 분배되었는지 먼저 확인해야 함
    - 50:50 실험이라면 A와 B의 사용자 수 차이가 통계적으로 유의하지 않아야 함
    - 트래픽이 50:50으로 분배되었는지 확인하기 위해 노출도 크게 차이가 없어야 함
    - 대시보드를 잘 구축한다면 다양한 조건으로 분석 가능

### **A/A Test**
- A/B 테스트 이전에 시스템이 정상인지 검증
    - 동일한 서비스를 두 그룹으로 분리
    - 주요 지표 비교
    - 모든 지표에서 통계적으로 ***유의미한 차이가 없어야 정상***
- 확인 항목
    - 표본 배정 비율과 사용자 중복 여부
    - 이벤트 수집 및 지표 계산의 일관성
    - 우연한 거짓 양성이 예상 범위 안에서 발생하는지

### **A/B Test의 통계**
- A/B Test의 목적은 두 가지 버전 중 어느 것이 더 좋은가?
- 두 가지가 있을 때
    - B가 정말 더 좋은가?
    - 아니면 우연히 좋아 보이는 것인가?
- 이때 사용하는 것이 통계적 검정(Statistical Test)
    - A와 B는 차이가 없다고 가정 = 동일하다고 가정하고 시작
    - Ex) A 전환율 = B 전환율 (B - A = 0)

### **통계 검정**
- 비율 비교(Proprotion)
    - CTR, Conversion Rate, Traffic Split처럼 0/1 이벤트의 비율을 비교하는 경우
    -> Proportion Z-Test 사용
    - CTR = Click/Impression
    - Conversion Rate(CVR) = Converted Users / Users
    - Traffic Split = B 사용자 수 / 전체 사용자 수
- 평균 비교 (Mean)
    - 평균 구매 금액, 평균 체류시간 처럼 연속형 값의 평균을 비교하는 경우
    -> Two-sample T-Test 사용
    - 평균 구매 금액
    - 평균 주문 금액
    - 평균 체류 시간

### **A/B Test의 통계
    - Z-score는 분포에서의 위치를 나타내는 값, P-value는 귀무가설이 참일 떄 현재 결과가 발생할 확률
    - Z-test는 Z-score를 이용해서 가설을 검정하는 방법
    - 샘플의 크기가 커지거나 A와 B간의 차이가 커질수록 통계적 유의성이 커짐

### **트래픽 균등성 검증**
- A/B 테스트를 분석하기 전에 가장 먼저 확인해야 하는 것은 트래픽이 정상적으로 분배되었는지 여부
- 50:50 실험이라면
    - A 그룹의 기대 비율 50%, B 그룹의 기대 비율 50%
    - A 그룹의 실제 비율 48%, B 그룹의 실제 비율 52%
- 우연히 발생한 것인지, 실험 시스템에 문제가 있는 것인지를 확인해야 함
-> 트래픽 균등성 검증
-> A/B Test 분석 전에 하상 가장 먼저 확인해야하는 지표

### **정규 분포를 사용할 수 있는 이유**
- 사용자가 B 그룹에 속하는 사건은 베르누이 분포를 따름
- 하지만 샘플 수가 충분히 많으면 중심극한정리(CLT)에 의해 표본 비율의 분포는 정규분포에 가까워짐
- 트래픽 비율 검증에는 Proportion Z-Test를 사용할 수 있음
    - 모집단에서 N개의 샘플을 통해서 나온 특정 이벤트의 확률의 평균이 P인 경우
    - 실제 트래픽 비율이 기대 비율 0.5 에서 얼마나 벗어났는지 계산
    - A/B 테스트가 정상적으로 동작한다면 P(A) = P(B), P(B)=0.5 사용자들이 50:50으로 나뉘어야 함
- Z-Test는 데이터의 평균이나 비율이 특정 값과 다른지 검정하는 통계 방법
    - Z-tset와 T-Test는 거의 같은 형태의 테스트
    - 큰 샘플이면 Z-Test, 작은 샘플이면 T-Test
    - 비율 비교에는 proportion z-test(클릭률, 구매율, 가입률, 트래픽 분배 비율 등)
    - 평균 비교에는 two-sample t-test(평균 구매금액, 평균 체류시간 등)

## A/B Test 예제
### **A/B Test 분석 흐름
- 실험 목표
    - A/B 그룹 분할
    - 지표 비교
    - 통계 검정 수행
- 확인하고자 하는 포인트
    - B가 A보다 더 좋은가?
    - 그 차이는 우연인가?

데이터 -> 그룹분할 -> 트래픽 균등성 검증 -> 지표계산 -> 검정 -> 결론  
User Data -> A/B 분할 -> Traffic Balance Check -> Conversion 비교 -> Z-test -> 유의성 판단

### ** 데이터 구조 이해 (user-level)**
- 컬럼 설명
    - user_id
    - impression (노출 수)
    - purchase (구매 수)
    - revenue (매출)
    - converted (전환 여부)

- 개념
    - conversion Rate = converted 평균
    - A :[True, False, True] -> 66%
    - B :[True, True, Ture] -> 100%

### **A/B 그룹 분할과 지표 검정**
- 분할 방법
    - user_id 기반 hash 사용
    - 동일 user -> 동일 그룹
- 이유
    - 실험 중 그룹 변경 방지
    - 재현 가능한 랜덤

- 비교지표
    - User
    - Purchases
    - Revenue
    - Conversion Rate

- Proportion Z-test
    - Z = (p1 - p2) / SE
    - 유의수준 5% 가정 ( |Z| > 1.96 -> 유의미, |Z| <= 1.96 -> 우연)

## **Evne-Level 분석**
### **User-Level vs Event-Level**
- User-Level 분석
    - 사용자 단위로 전환 여부/매출을 집계
    - B가 A보다 유의미하게 좋은가?
- Evnet-Level 분석
    - 노출, 클릭, 구매, 매출 이벤트를 단게별로 분석
    - 어디에서 차이가 발생했는가?
- OLAP Cube
    - Event/User 데이터를 여러 차원으로 미리 집계
    - 대시보드를 구성한다면 빠르게 필터링하고 비교 가능
- A/B Test 핵심 KPI 주요 지표 예시
    - CTR = Click / Impression -> 관심 또는 반응
    - CVR = Converted Users / Users -> 전환 성과
    - ARPU - Revenue / Users -> 사용자당 매출 성과

### **A/B Test 결과 분석 (Event-Level)
- 실습 목표
    - Raw 이벤트 데이터를 분석용 구조로 변환
    - KPI 계산 (CTR, CVR, Revenue)

- 왜 OLAP Cube를 사용하는가?
    - Raw 데이터 문제
    - row 수 많음
        - 계산 느림
        -> 미리 집계 (Cube)
    - 빠른 분석
    - 리포트/대시보드 시각화 도구 연결 가능

- 실습 목표 흐름
    Raw Data -> Bucket Data Join -> Base Table 생성 -> KPI 계산 -> OLAP Cube -> 리포트

### **A/B Test 분석 요구사항**
- 핵심 지표 비교 기능
    - A/B 테스트 전체 기간 동안 주요 지표를 비교할 수 있어야함
    - 핵심 지표 (KPI)비교가 필요
    - 매출, 구매, 클릭, 노출
- 시간 흐름(Trend) 분석 기능
    - 일별 단위로 핵심 지표의 변화를 확인할 수 있어야 함
- 통계적 유의성 표시
    - 핵심 지표 변화가 통계적으로 의미 있는지 색상 등으로 표시
- 사용자 메타데이터 기반 필터링
    - 성별, 연령, 지역, 디바이스, 유입 채널 등 기준으로 분석 가능

### **A/B Test에서의 고려사항**
- 필터 조건에 따라 통계 계산이 달라진다
    - 리포트/대시보드에서는 다양한 조건으로 데이터를 필터링할 수 있음
        - 날씨, 사용자 속성(성별 연령 등), Varlant (A/B)
    - 이때 선택된 데이터 기준으로 z-score 같은 통계값이 다시 계산되어야 함
- 데이터 처리 방식
    - 방법 1
        - raw 데이터를 매번 다시 집계
        -> 속도가 느려질 수 있음
    - 방법 2
        - 미리 집계 데이터를 만들어 사용
        -> OLAP Cube 방식

### **OLAP Cube**
- 여러 분석 조건(Dimension) 별로 필요한 지표(Metric)를 미리 집계해 둔 데이터 구조
    - Raw Event 데이터를 매번 다시 계산하지 않고 빠르게 조회할 수 있음
    - 대시보드에서 날짜, 실험군, 성별, 연령대, 디바이스 드응로 필터링 가능
- Demension 예시
    - 날짜, Varlant(A/B), Gender, Age Group
- Metric 예시
    - Users, Imporessions, Clicks, Purchases, Revenue

### **실험 결과 의사결정**
- 유의미하게 좋아짐 : B 적용을 검토
- 차이 없음 : 기존 유지 또는 새로운 가설 수립
- 유의미하게 나빠짐 : 실험 중단 및 원인 분석
- Primary Metric은 좋아졌지만 Guardrail이 악화되면 적용 보류
- 통계적 유의성과 비즈니스 의미를 함께 보고 판단
